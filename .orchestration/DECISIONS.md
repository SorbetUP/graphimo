# Graphimo Decisions and Questions

## Decisions

- **D-001 — Product authority:** The PDF's requirements take precedence over the existing implementation and screenshots. Marimo owns notebook source/DAG/execution; Graphimo owns presentation metadata and the Zeron interface.
- **D-002 — Delivery slice:** Implement the explicitly documented sidecar `Path` key defect first because it is reproducible, isolated, and protects notebook layout persistence without inventing architecture. Full v0.2 acceptance remains the target and cannot be claimed from this slice.
- **D-003 — Test independence:** Developer and regression-test writer work from the same baseline in separate worktrees. The test writer must first demonstrate failure against baseline before integrating with implementation.
- **D-004 — Python distribution boundary:** The Python package explicitly includes `adapter`; `plugin/` is Zeron Luau source, and `components/`/`examples/` are project content. Fixed setuptools discovery in `ec747c2`, added the independent wheel test in `c21a355`, and verified the documented editable install plus import from the main checkout. Resolved.
- **D-005 — Component library metadata and search:** Reuse the `category` array and callable metadata already emitted by the production bridge, and the installed `@ds/search_field` from the Zeron `0.3.7` bundle. A pure `Library.project(components, query)` seam keeps grouping/filter behavior testable without changing bridge/runtime APIs. Planner approved this bounded UI leaf; broader component parameters/ports remain separate.
- **D-006 — Safe parameter metadata and signature rendering:** Match the Python adapter and Luau bridge using `has_default`, JSON-scalar-only defaults, and conservative display annotation serialization. The existing signature string remains available, but must be built from sanitized parameter metadata so arbitrary annotation/default repr methods are not invoked; ordinary supported signatures remain readable. Do not resolve forward references or invoke arbitrary annotation formatting. Only safe scalar `typing.Literal` values become choices; enum support and editor controls are deferred. This keeps imported component metadata JSON-safe without extending execution or source-edit behavior.
- **Q-004 — Existing signature formatting safety:** `str(inspect.signature(value))` could invoke arbitrary annotation/default repr methods, conflicting with safe metadata serialization. Resolved in D-006 by rendering a sanitized signature: preserve parameter structure, keep supported values readable, omit unsupported annotations, and use `...` for unsupported defaults. A raising sentinel test covers the regression.
- **D-007 — Literal display annotation:** Safe scalar `typing.Literal` values produce deterministic Python-syntax `Literal[...]` text in both `annotation` and `signature`, and ordered `choices`. Use `repr` only for exact JSON scalar types so `True`/`None` remain valid Python syntax; never repr arbitrary values. If any Literal value is unsupported, omit both annotation text and choices. Planner confirmed after the independent test exposed that choices alone were insufficient.
- **D-008 — Portable Literal recognition:** The Luau-generated Python discovery script must not hardcode private typing runtime class names, which differ across Python 3.11/3.13. Use `type(typing.Literal[0])` as an exact alias-type guard, confirm `annotation.__origin__ is typing.Literal`, and use `typing.get_args`; this avoids touching attributes on arbitrary annotation objects.
- **D-009 — First editor slice safety:** Editors cover only supported optional defaults with exact annotation/default compatibility; unannotated values infer from exact types. Exact integer range is ±(2^53−1) to preserve JSON number precision. Safe setters may add a missing optional keyword based on discovered defaults, but never synthesize a missing required input.
- **D-010 — v0.5 is directional draft:** User supplied `Graphimo_Structuration_fonctionnelle_v0_5.pdf` and asked to continue with it in mind. Adopt its stated thin-layer/source-of-truth direction and acted Base/Control/Display/Annotation/Group/Meta taxonomy; keep strong proposals and §19 open questions distinct. Do not treat its roadmap as blanket implementation authorization. The pending v0.2 parameter-editor leaf is stale until reconciled with a v0.5 Base Block contract.
- **D-011 — Base Block projection scope:** First v0.5-aligned leaf is read-only static contract metadata and instance projection for generated function-backed blocks. Use safe `inspect.signature` + AST/source analysis; tuple splitting requires fixed annotation arity and tuple literals at every value-return path. Scalar classification must match between adapter and production bridge: safe scalar annotations include `Literal[...]`; unannotated constants count only when exact finite JSON scalars. Ambiguity collapses to one object output. Add an explicit callable marker to new generated cells; exact component/callable/hash markers and assignment/call must agree. Production linkage is `{component_id, callable, source_sha256}`; legacy two-marker cells remain generic. Projection items are `{cell_id, component_id, callable, inputs, outputs, output_mode}`. UI, actual tuple indexing/connections, and the §19 questions remain deferred.
- **D-012 — Base Block card summary:** Next v0.5 slice renders ordered, read-only input/output contract labels only for exact generated component cards. Generic cards remain as-is. It does not make those labels interactive ports or decide connection/display/run semantics.

## Questions / status

- **Q-001 — Host verification:** Can this environment open the currently installed Zeron plugin and expose its signing/install state? Status: partially answered. Zeron Settings → Plugins → Installed showed Graphimo enabled at 0.2.1; clicking the Graphimo nav entry rendered the page and showed `/Users/sorbet/Desktop/notebook.py` with two marimo cells. This does not prove the locally changed artifact was installed or exercise New/Open, output, permissions, signing, or recovery scenarios.
- **Q-002 — Current SDK surface:** Which Zeron SDK/API version is installed, and does it support the PDF-proposed service/watch/network surfaces? Status: partial inspection complete. Running app is Zeron `0.3.7` / build `0.3.7.9999`. App-bundled Git and GitHub helper copies are identical. Both app helper and repo's `plugin/zeron.luau` expose `M.service`; `M.run`, `M.page`, and `M.tool` are also shared. The local Graphimo helper is a modified copy: callback-based `ToolAdapter.dispatch` for tools and a different `zeron.on` return shape, so retain it together with `tool_adapter.luau`. `serve`, `watch`, `fetch`, and `emit` were not found in either inspected helper. A full SDK/manifest capability audit (including runtime permissions/network scoping) remains open; don't assume PDF-proposed APIs based on names alone.
- **Q-003 — Sidecar scope:** Keep the existing absolute resolved notebook path as JSON key for backward compatibility in this fix; relative portable keys are a separate design choice and are not required to correct the serialization mismatch.
- **Q-005 — Active architecture source:** v0.2 describes a more cell-centric visual; v0.5 redefines functional Base Blocks, controls, displays, annotations, referenced groups, and specialized Meta Blocks. Status: user has asked to continue with v0.5 in mind; v0.5 labels itself a draft. Adopt stated direction, retain open questions, and let the planner select only an implementation-ready next leaf.
- **Q-006 — Connected defaults and disconnect semantics (Open):** When a default-backed optional input is connected, should the Python default become dormant, remain an active fallback, or be removed? What source edit restores behavior on disconnect? This is an owner decision because the answer changes notebook source and runtime behavior. Until resolved, Base Block descriptors remain read-only metadata and marimo `refs`/`defs` remain the sole edge truth.
- **Q-007 — Callable pin mapping (Open):** Which optional default parameters appear as callable input pins, and how are required refs distinguished from descriptive signature metadata? How do tuple output descriptors map to independently connectable values when Python only exposes a single expression result? Do not infer executable pins from static descriptors alone.
- **D-013 — Existing canvas/runtime seam audit:** `Canvas.port`, `Canvas.draw_edges`, and drag hit tests derive geometry from marimo `refs`/`defs`; `Bridge.connect` AST-edits and compiles source before replacement. The adapter and production Luau bridge differ in accepted call shapes. Any connection work must preserve marimo graph truth and first establish parity/refusal tests. No changes made.
- **D-014 — Read-only Control Block inventory boundary:** For a separate metadata-only leaf, accept the audited private marimo `0.25.2` `UIElement`/`slider`/`dropdown` classes and `ctx.globals`, with an exact-version guard and fail-closed behavior. Inventory only exact slider/dropdown instances; do not render or mutate widgets. This does not decide or implement interactive Zeron Control Blocks.
- **Q-008 — Control Block runtime/rendering boundary (Open):** marimo 0.25.2 exposes real `marimo.ui` widget objects via live runtime globals, but enumeration/binding metadata relies on private context/registry/classes; current Bridge.inspect omits these objects. A metadata-only allowlisted projection is feasible to test live, but Zeron interactive rendering needs a separate embedding decision. Do not use source heuristics or treat metadata as a completed Control Block.
